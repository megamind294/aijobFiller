# JobPilot implementation gaps against the supplied Tsenta observations

Read-only source audit, 18 October 2026. Target: `docs/jobpilot-master-observations.md`. This report inspects local source and test definitions; no tests, provider calls, live deployment checks, employer submissions, payments or mailbox reads were performed. Existing UI and code are not proof that a production provider is connected. Tsenta descriptions in the source document retain their original observed/inferred/unverified labels.

## Main finding

JobPilot has real Flask, SQLite and file-backed workflows, rather than only screens. Its largest parity gaps are source coverage, real employer adapter coverage, action-capable assistance, rich document editing and external-service completion. Replacing the existing application wholesale would discard working authorization, immutable packages and accounting safeguards.

## Practical build order

1. Preserve existing account/data/approval/ledger invariants. Reconcile stale delivery documents with committed source and deployed version; `docs/PAGE_REPAIR_CHECKLIST.md` mixes earlier pending statements with later configuration checkpoints.
2. Establish a real user acceptance path: registration → paid access (sandbox first) → upload/OCR/correction → verified profile → real discovery → exact package review → supported execution or honest manual handoff → receipt/tracker.
3. Expand discovery sources with provenance and stale-job behavior; separately implement and prove a small explicit employer adapter set before increasing advertised coverage.
4. Implement the document editor behaviors observed in the supplied blueprint, with versioning and invalidated approvals after changes. Keep AI consent/source provenance visible.
5. Complete Gmail consent/routing proof; decide separately whether local drafts, Gmail drafts, sending and calendar integration are required. New mutation permissions need explicit product/user authorization.
6. Add assistant action tools only over existing guarded services. Add real research provider and secondary clients after core acceptance is proven.

## Test evidence boundary

Relevant source-defined tests include `tests/test_web_discovery.py` (live-source mocking, failures, account isolation), `tests/test_ai_preparation.py` (consent, constrained rewrites, cap, immutable source), `tests/test_web_applications.py` (review, manual attestation, active-worker conflicts), `tests/test_web_inbox.py` (OAuth/CSRF/isolation, local-only AI draft, failed-ingestion cursor behavior), and the billing, worker, profile and API/MCP suites. These are test definitions, not a fresh passing result. Provider mocks and localhost forms cannot establish real employer/provider success.

- Provider consent/status and one bounded end-to-end proof per enabled external integration.
- Real supported-origin execution evidence under explicit user authorization; no mass/live submissions as an audit side effect.
